# D9.0 — Decision 9 contract-freeze proposal

Status: **proposed for approval; design-only and synthetic-only**. Decision 9 is approved, but this D9.0 contract set is not yet approved for implementation or operational use. It defines messages and validation rules for later D9 tranches. It does not create a launcher, importer, database writer, collector, processor, scanner, custody store, credential, runtime principal, bootstrap event, evidence row, API, export, search surface, or frontend integration.

## Purpose and fixed boundary

D9.0 turns the approved Decision 9 trust boundary into versioned, machine-readable contracts before executable components exist. Its purpose is to make later implementations independently testable and to prevent a launcher, importer, adapter, or recovery tool from inventing fields, outcomes, limits, or privileges at runtime.

The contract set inherits without changing:

- migrations 001–005 and the empty migration-005 Tranche 2A schema;
- the approved `jedi-atlas-evidence-bundle` version `1.0.0` manifest, canonicalization profile, and evidence semantics;
- the two-bundle pilot: one evidence-empty bootstrap bundle, followed only after separate approval by one raw-document bundle;
- the network-free importer, fixed-function writer, disposable database candidate, independent verifier, atomic promoter, restricted local content-addressed store, and separately verified backup architecture;
- the rule that attribution is not authentication, a clearance is not a legal-rights conclusion, and technical acceptance is not source verification, legal review, publication, or public eligibility.

The words **must**, **must not**, **required**, and **only** below describe the proposed compatibility contract. They do not claim that a control is currently enforced. Contract validation can test bytes and messages; it cannot prove kernel identity, authorization, filesystem confinement, process isolation, malware absence, durable `fsync`, atomic promotion, or human review. Those controls remain implementation and operating prerequisites in later D9 tranches.

Schema files and synthetic fixtures are version-controlled. Real profiles, identity maps, handoffs, permits, certificates, clearances, journal events, state seals, adapter capabilities, and results are operational instances and must not be committed to Git. Authentication credentials, signing/private keys, encryption keys, session material, and secret values are never fields in these formats.

The machine inventory is [`contract-catalog-v1.json`](schema/d9-0/contract-catalog-v1.json). It pins the exact raw SHA-256 of one shared-definition schema, nine top-level schemas, one protected operational-helper schema, the closed [`classifications-v1.json`](schema/d9-0/classifications-v1.json), the field registry, and the [`digest-profiles-v1.json`](schema/d9-0/digest-profiles-v1.json) registry. The digest registry fixes the exact payload profiles, pointer-scoped bindings, exact-byte resolvers, and complete SQLite projections used by the pilot. Those profiles cover exact named bytes; a closed canonical contract record omitting only its top-level self-digest; the approved evidence manifest omitting only its top-level bundle digest; complete canonical objects with no omission; normalized complete and legacy SQLite schema inventories; raw deterministic-ID table rows; the specially projected receipt row resolved by its unique bundle tuple; the exact object inventory; the accepted-receipt dependency graph; the prohibited-surface inventory; protected custody-capability issuance/control records; and clearance/pre-promotion scopes. The golden file contains independently fixed canonicalization, complete-manifest, nested-payload, contract-record, and raw-file hashes; the JavaScript validator consumes but never regenerates those expected values. The validator recursively enumerates the contract-root files and rejects any missing, substituted, or unexpected file. Every regular file is covered by the exact raw-file inventory except the golden file itself: that single self-unhashed exception avoids an impossible self-reference, while the reviewed repository commit and contract-root inventory bind its bytes. The catalog, field registry, and digest-profile registry likewise have no self-digest; their exact raw bytes are pinned externally by the applicable inventory. Exact counts are derived and reported by the offline validator rather than duplicated as normative prose.

## Common envelope, serialization, and hashing

Each format has a closed top-level object with `format`, `format_version`, its format-specific stable identifier, and exactly the fields listed by its schema. Every protected record format except the bounded `jedi-atlas-import-result` has a top-level `record_digest_sha256`; the result is deliberately operational and is not self-digested. Schema `additionalProperties: false` closes every object. The contract validator additionally rejects credential-shaped keys and secret-like values; JSON Schema does not perform semantic secret detection by itself.

Version 1 reuses the approved evidence-bundle canonical JSON profile:

1. Read a bounded byte sequence and decode strict UTF-8. Reject a BOM, invalid UTF-8, empty input, duplicate object keys, and lone UTF-16 surrogates.
2. Preserve valid Unicode scalar values exactly. Perform no NFC, NFD, case, line-ending, or other value normalization.
3. Permit objects, arrays, strings, booleans, null, and nonnegative safe integers from `0` through `9007199254740991`. Reject fractions, exponents, negative values, and source token `-0`.
4. Sort object keys lexicographically by UTF-16 code units. Preserve array order exactly.
5. Serialize strings using ECMAScript `JSON.stringify` escaping and objects/arrays compactly, with no insignificant whitespace and no trailing line ending.
6. For a self-digested object, omit only that schema's named top-level digest member, canonicalize every other member, UTF-8 encode the result, and compute SHA-256. Nested fields with the same spelling are not omitted.
7. Digests are exactly 64 lowercase hexadecimal characters. The contract schema and independent golden vector fix the omitted field and payload for each format.

Array order is data, never an incidental parser or filesystem order. Arrays that describe an ordered protocol preserve declared order. Arrays that represent a logical set must arrive in the one order fixed by the semantic validator: migrations by approved numeric filename; component releases and identity bindings by `runtime_role_code`; operational profiles by `profile_kind_code`; logical handle slots by `slot_code`; required scanners by `scanner_code`; write-surface table names and forbidden operation codes in their frozen lists; and logical-state inventories by their declared deterministic projection keys. Reordering any of these changes the canonical bytes or fails semantic validation. Consumers must not sort an arbitrary instance and then accept it silently.

A hash authenticates neither its producer nor its meaning. Protected issuers must bind canonical contract bytes to an authenticated channel or separately approved signature/attestation mechanism in later tranches. D9.0 does not create keys or select a credential store.

The clearance record pins scanner build/rules digests and result completion times, but it does not contain a rules/signature issuance timestamp. Therefore the later launcher/scanner integration must resolve those hashes against an authenticated protected scanner registry and enforce the 86,400-second engine/rules/signature ceiling at operation start. D9.0 validates the ceiling and the 3,600-second result-age calculation; it cannot derive rules age from a clearance payload alone.

Paths must be normalized relative paths. Reject absolute, empty, dot, dot-dot, duplicate-separator, backslash, NUL, C0-control, DEL, or over-limit paths; symlinks, magic links, mount crossing, directories, devices, FIFOs, sockets, unexpected owner/mode, sparse anomalies, and a staged inode link count other than exactly one. The schema can enforce only lexical rules. Descriptor-relative `openat2`/equivalent confinement, file type, ownership, link count, mount, and time-of-check/time-of-use protections remain D9.1–D9.4 implementation duties.

The IPC profile is Linux `AF_UNIX` with `SOCK_SEQPACKET`. One packet contains one canonical JSON object and no trailing bytes. Descriptor roles and ordinals are declared in the object and must match the ancillary `SCM_RIGHTS` list exactly; missing, extra, repeated, wrong-order, or wrong-type descriptors fail closed. Endpoints additionally require filesystem ACLs, an allowlisted kernel peer credential, a unique operation nonce, and a compatible contract/profile digest. JSON fields never treat a numeric file descriptor or a pathname as authority.

## Identity and runtime-binding semantics

The runtime profile names logical descriptor slots and component/endpoint codes, never credentials or caller-controlled absolute paths. It pins a runtime-domain commitment; the exact evidence-manifest schema digest; migrations 001–005; complete and legacy schema commitments; exact object-inventory and prohibited-surface commitments; twelve executable and dependency-lock commitments; handoff, scanner-registry, clearance, journal, backup and custody-adapter profile generations; backend mapping; exact limits; and allowed/forbidden write surfaces. The separately issued identity-binding record pins this runtime profile and the same runtime-domain commitment. In the frozen pilot, the candidate writer is limited to the nine Tranche 2A tables plus the exact bootstrap roster in `atlas_principals`, while legacy, nonprincipal Tranche 1A, Tranche 2B, review/publication, and application surfaces remain denied.

The binding set is immutable and carries one inclusive issue time, one exclusive expiry time, and per-binding validity intervals. Each binding states the runtime role, authenticated subject kind, subject identifier or protected pseudonym, expected executable/build digest where applicable, allowed IPC endpoint and operation modes, validity interval, and Atlas principal code only for roles that create Atlas attribution. The classification registry closes the exact 19-row role-to-kind, role-to-endpoint, and role-to-operation-mode matrix. It also closes the twelve logical-handle recipient/access lists: in particular, only `journal_broker` receives the append-intended operation-journal handle; the recovery writer and verifier receive only the separate named disposable `recovery_database` handle; the custody adapter and independent verifier receive read-only `handoff_registry` access needed to resolve exact protected seals/handoffs; and the independent verifier, trusted launcher, and cloner/promoter receive read-only `clearance_register` access needed respectively to authorize, launch, and consume an exact current pre-promotion record. The only clearance-register writer remains the fixed-function clearance broker. Merely originating or consuming a journal event confers no journal-handle access. Permit-scope handle lists are policy metadata at D9.0, not proof of runtime confinement. D9.1 must implement, authenticate, and adversarially test per-permit descriptor issuance and revocation before any claim of handle isolation is valid. D9.0 pins one exact supplied generation and rejects an expired, unknown, changed, or mismatched record; it does **not** define an active-generation registry, revocation event, or replacement-selection algorithm. D9.1 must choose and protect those lifecycle semantics before launch, then pin and recheck the selected record at the operation boundaries.

The controlled pilot requires exactly 19 role bindings—seven human and twelve service bindings—with one binding per role:

- one kernel-authenticated human `human_submitter` bound to the one human Atlas principal;
- one service `collector` bound to the collector Atlas principal and immutable runner build/profile;
- one distinct service `bundle_importer` bound to the importer Atlas principal and immutable release build;
- separately authenticated operational services `trusted_launcher`, `database_writer`, `cloner_promoter`, `independent_verifier`, `custody_adapter`, `handoff_broker`, `clearance_broker`, `journal_broker`, `scanner`, and `backup_adapter`, which do not become Atlas principals merely because they participate operationally;
- distinct authenticated human bindings for `operational_witness`, `bootstrap_authority`, `clearance_decider`, `clearance_checker`, `recovery_operator`, and `recovery_authority`; none is inferred from a manifest or Atlas principal row;
- no processor binding. Processing and candidate creation remain denied in the initial profile.

The human submitter, collector, and importer must be distinct bindings. Manifest codes, environment variables, command arguments, commit authorship, and caller-supplied IDs never select or authenticate a principal.

## Collector handoff and bundle seal

A `collector_handoff` is created by the collector handoff broker after the collector closes its frozen staged output. It binds its own stable record ID, the broker binding, collection profile and request-configuration digests, retrieval-event code, artifact byte layer/SHA-256/length, staged-object identity, collector principal/software/version, actual immutable runner-build digest, collection completion time, handoff time, and expiry. It does not need the later edited bundle digest and cannot authorize import.

If the captured request was conditional, its fingerprint resolves the named basis event exactly once across the retained manifest lineage and includes the basis bundle ID, sequence, digest, event code, validator kind, and validator value. The resolver reopens every manifest needed for that lineage and recomputes its canonical bundle digest from its bytes; a digest string merely copied from another contract is not a valid pin. The basis must be an earlier retained HTTP-200 full representation under the same request method and representation profile. A missing, duplicated, stale-owner, unpinned, wrong-profile, or partially declared basis fails closed; a later manifest's tuple is never substituted for the tuple that actually owns the basis event.

After human review, the separately bound `trusted_launcher` creates a `bundle_seal` that binds the immutable reviewed-root snapshot, Git commit, manifest relative path, bundle ID/sequence/digest, runtime-profile digest, identity-binding digest, operation nonce, authenticated submitter/importer bindings, launcher binding, target logical state, seal time, and expiry. The cardinality is structural: a `principal_bootstrap` seal has exactly zero collector-handoff references, while a `single_document` seal has exactly one matching collector-handoff reference. The importer accepts historical collector attribution only when the receipt and document seal both verify and match the manifest exactly. The handoff broker may record the collector receipt; it cannot mint either post-review bundle seal.

The handoff records contain no document bytes, full URL, request/response headers, credentials, arbitrary filesystem paths, scanner output, or candidate/legal content. Expiry before promotion blocks the operation; it does not rewrite a previously accepted evidence receipt. D9.0 defines no handoff-revocation record or active-handoff registry. Any such lifecycle mechanism is a D9.1 implementation decision and may only narrow future acceptance, never rewrite an accepted receipt.

## Bootstrap permit and replay certificate

The bootstrap permit is an immutable issuance. Its payload pins:

- one permit ID and canonical-lineage ID;
- mode `bootstrap` and the expected empty logical-state seal;
- the reviewed Git commit, manifest path, sequence `1`, bundle ID, and bundle digest;
- the importer release, runtime-profile, and binding-set digests, while the separately verified bundle seal binds the same manifest, bundle, submitter, importer, operation nonce, and target state;
- the authenticated human submitter and independent witness bindings;
- the distinct authenticated bootstrap-authority binding that issued the permit;
- the SHA-256 commitment to the exact four-principal roster, whose full ordered contents appear in the resulting logical-state seal;
- one operation nonce, issue time, not-before time, and expiry time.

Permit state is not a mutable field on an issuance. Each append-only `permit_transition` targets the current predecessor, pins the operation and nonce, the observed logical-state seal (or the closed optional last-known value on an ambiguity edge), reason, semantic occurrence time and recorder role/binding, and the distinct `trusted_launcher` append-broker binding and protected persistence time. `occurred_at` states when the authorized actor says the semantic event occurred; `persisted_at` states when the trusted launcher actually appended that immutable record. The latter is the knowledge boundary: `occurred_at <= persisted_at`, successor persistence is strictly increasing, and both times must precede the permit's exclusive expiry. `recorded_by_*` describes who is responsible for the transition's meaning; `persisted_by_binding_code` and `persisted_at` describe the authenticated fixed-function broker and append chronology. The broker cannot manufacture the semantic recorder's authority, and a caller-supplied binding code proves neither identity nor authorization. The closed transition table is:

| Permit | From | To | Transition / reason | Extra authority |
|---|---|---|---|---|
| bootstrap | `ready` | `in_progress` | `operation_claimed` / `operation_claimed` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| bootstrap | `ready` | `revoked` | `authority_withdrawal` / `authority_withdrawal` | exact issuing `bootstrap_authority`; at or after issuance and before expiry, including before `not_before` |
| bootstrap | `in_progress` | `spent` | `verified_effect` / `canonical_receipt_verified` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| bootstrap | `in_progress` | `recovery_required` | `state_ambiguous` / `state_ambiguous` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| recovery | `ready` | `in_progress` | `operation_claimed` / `operation_claimed` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| recovery | `ready` | `revoked` | `authority_withdrawal` / `authority_withdrawal` | exact issuing `recovery_authority`; at or after issuance and before expiry, including before `not_before` |
| recovery | `in_progress` | `spent` | `verified_effect` / `canonical_receipt_verified` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| recovery | `in_progress` | `recovery_required` | `state_ambiguous` / `state_ambiguous` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| post-promotion completion | `ready` | `in_progress` | `operation_claimed` / `operation_claimed` | exact `trusted_launcher`; at or after `not_before` and before expiry |
| post-promotion completion | `ready` | `revoked` | `authority_withdrawal` / `authority_withdrawal` | exact issuing `recovery_authority`; at or after issuance and before expiry, including before `not_before` |
| post-promotion completion | `in_progress` | `spent` | `no_effect_verified` / `no_effect_verified` | exact `independent_verifier`; at or after `not_before` and before expiry |
| post-promotion completion | `in_progress` | `recovery_required` | `state_ambiguous` / `state_ambiguous` | exact `independent_verifier`; at or after `not_before` and before expiry |

A bootstrap permit lasts no more than 3,600,000 milliseconds; recovery and post-promotion-completion permits last no more than 900,000 milliseconds. A permit may be claimed only when at least 60,000 milliseconds remain before its exclusive expiry. This refuses near-expiry work while retaining a usable claim window. The deterministic lifecycle projection takes one canonical `as_of` timestamp and first selects only transitions whose protected `persisted_at <= as_of`; it never orders knowledge by a caller-supplied semantic occurrence time. Before issuance no lifecycle is visible. An unclaimed permit is `ready` before expiry and derives `terminal_expired_unused` at expiry. A claimed permit is `in_progress` before expiry and derives `terminal_recovery_hold` at expiry. A persisted terminal transition yields `revoked`, `spent`, or `recovery_required`. Every consumer evaluates this protected-time projection at its own use time: an operational journal event requires the claim itself to be the visible head, while a replay certificate or bootstrap completion permit requires the cited `spent` transition to be the visible head no later than certificate or permit issuance. Equality with a terminal transition's `persisted_at` means that terminal is already visible and cannot authorize another claimed-state event. Because a transition may be persisted only before expiry, no later append is accepted after either derived expiry state even when its `occurred_at` is backdated. A reused, branched, expired, wrong-lineage, wrong-bundle, wrong-predecessor, wrong semantic recorder, wrong append broker, or unregistered transition is rejected. The handoff broker has no permit-transition authority. `revoked`, `spent`, `recovery_required`, `terminal_expired_unused`, and `terminal_recovery_hold` are terminal for all three permit kinds. In particular, an ambiguous first bootstrap cannot produce a replay certificate or be relabelled as accepted evidence. Its target and operational evidence remain quarantined, and ordinary writes remain locked. Restarting requires a later separately approved incident procedure, a newly reviewed runtime/binding/seal/permit set, a proven fresh empty isolated target, and a new canonical lineage; it never resumes, mutates, or adopts the ambiguous target. This deliberately fail-closed boundary avoids inventing an under-specified ambiguity-resolution authority in D9.0.

After verified first acceptance, an independent-verifier replay certificate binds the accepted sequence-1 bundle tuple and deterministic receipt-row digest, exact principal roster, canonical-lineage ID, resulting logical-state seal, spent bootstrap transition, issuer, witness, issue/expiry times, and disposable-recovery-only class. A receipt has no invented operational record code: it is resolved by the physical unique tuple `(bundle_code, bundle_sequence, bundle_digest_sha256)` and then projected through the frozen receipt-row profile. The certificate is an attestation, not authorization by itself.

An exact-operation `recovery_permit` issued by the separately bound human `recovery_authority` is also required. It binds the incident and restore-plan commitments; operation ID/nonce; accepted bootstrap bundle, replay certificate, and accepted logical state; the expected empty target state; a named disposable recovery database; runtime/binding/importer commitments; distinct recovery operator, witness, and issuer bindings; scope `exact_bootstrap_reconstruction_only`; and a validity interval of at most 900,000 milliseconds. The permit is usable from inclusive `not_before` to exclusive `expires_at` and must not outlive either the replay certificate or the pinned identity-binding generation. It can authorize only that reconstruction. It cannot authorize another canonical first acceptance, a changed roster or bundle, ordinary import, direct canonical writes, or public use. An identical accepted-bundle no-op consumes neither a new permit nor the replay certificate.

The synthetic contract set includes both a genesis `logical_state_empty` and a real successor `logical_state_bootstrap`: the latter commits to the exact four-principal roster, accepted sequence-1 receipt/head, principal/receipt row projections, unchanged migrations and legacy state, empty remaining Atlas tables, and the prior logical seal. Permit and replay/recovery fixtures reference these concrete states instead of placeholder hashes.

The separate `post_promotion_completion` permit is available only after an independent verifier has established an exact canonical receipt and logical-state seal. It pins the target bundle kind as well as its tuple, the current terminal source-journal head, and the exact source authorization. For a document, the source authorization is the exact launcher-created single-document bundle seal. For bootstrap, it is the exact bootstrap-permit issuance plus its current ordinary `spent`/`verified_effect` terminal transition. It authorizes no canonical database write and may only complete the pinned backup/journal duties. It does not resolve an ambiguous first-bootstrap permit or turn `possibly_promoted` into an accepted bootstrap. Accordingly, `PROMOTION_STATE_AMBIGUOUS` is an eligible source error only for a `single_document` bundle. For either bundle kind, `FINAL_BACKUP_FAILED` and `JOURNAL_COMPLETION_WRITE_FAILED` are eligible only with an independently verified `promoted_verified` state. Completion succeeds only when the current completion-journal head is the exact authorized terminal event and the required backup inventory is verified; then the independent verifier records `no_effect_verified`, while the trusted launcher appends that transition.

## Custody-adapter message semantics

The v1 adapter protocol is a closed request/response union:

| Operation | Exact request material | Successful result | Failure outcomes |
|---|---|---|---|
| `open_staged` | staging-root slot plus normalized relative path; no incoming descriptor | `opened`, exact artifact, digest-bound source-handle capability envelope, one `staged_source` read-only regular-file descriptor | `rejected` or `retryable_failure` |
| `prepare` | exact artifact plus source-handle capability and one `staged_source` descriptor | `prepared` plus digest-bound single-operation preparation capability; no descriptor | `rejected` or `retryable_failure` |
| `verify_prepared` | exact artifact plus preparation capability; no descriptor | `verified`, echoing artifact and capability envelope; no descriptor | `corrupt`, `rejected`, or `retryable_failure` |
| `publish_no_replace` | exact artifact, protected backend code, recomputed content-addressed reference, and verified preparation capability; no descriptor | `published` or `reused_verified`, echoing identity/location plus durability receipt; no descriptor | `corrupt`, `rejected`, or `retryable_failure` |
| `seal_custody_access` | exact artifact/copy/backend identity, current clearance identity/scope, and pilot-v1 purpose exactly `integrity`; no caller-selected evaluation time, knowledge sequence, or custody leaf | `sealed`, with adapter-selected `custody_evaluated_at`, current accepted-bundle sequence, exact custody-leaf digest, clearance references, and a short-lived sealed-custody-access capability | `rejected` or `retryable_failure` |
| `open_custody` | exact artifact/copy/backend identity, pilot-v1 purpose exactly `integrity`, and short-lived sealed-custody-access capability; no caller-selected evaluation time or knowledge sequence | `available`, with adapter-selected `custody_evaluated_at`, current accepted-bundle sequence, exact clearance/custody-leaf references, echoed custody identity, and one `custody_source` read-only regular-file descriptor | `corrupt`, `rejected`, or `retryable_failure` |
| `abandon_temp` | adapter-issued preparation capability; no descriptor | `abandoned` or idempotent `already_absent`, echoing only that capability envelope; no descriptor | `rejected` or `retryable_failure` |

Every request and response binds the format/version, profile digest, operation ID, monotonic per-operation message sequence, nonce, operation discriminator, sender/recipient bindings, descriptor-role declarations, and request digest. Replay state is keyed by `(runtime-profile digest, operation ID, operation nonce, requester binding, adapter binding)`. Request sequences start at 1 and are contiguous; request IDs are unique within that tuple; a response reverses the peer direction, repeats the operation/request/sequence/nonce, pins the exact request-record digest, and exists at most once. A gap, duplicate request, second response, cross-operation capability, peer swap, nonce reuse, or mismatched digest fails closed.

The three capability envelopes are structured, highly restricted projections of exact protected issuance records. Each envelope binds capability kind and issuance-record digest, issuer/requester/adapter, operation ID/nonce, runtime-profile and identity-binding digests, exact artifact, allowed consumers, replay policy, and issue/expiry times. The protected issuance additionally pins the exact request or clearance/custody scope that created the authority. Issuances and their append-only transitions live in a protected short-lived state store through expiry or reconciliation; they never appear in Git, Atlas SQLite, results, or journals. Only the minimized envelope travels over authenticated custody IPC. The consumer resolves the issuance by digest, recomputes it, verifies the envelope is its exact projection, verifies authenticated peers and scope, and applies the closed transition graph. Possession or knowledge of a digest alone never authenticates or authorizes a caller.

The capability graph is deterministic. A source-handle issuance starts `ready` and is atomically claimed as `consumed` when one authenticated `prepare` request is accepted, within 30 seconds. A preparation issuance starts `ready`, becomes `verified` only with the exact successful `verify_prepared` response, and then becomes `consumed` only with the exact successful `publish_no_replace` response; alternatively `ready` or `verified` may become `abandoned` through the exact successful `abandon_temp` response, all within 15 minutes. A sealed-custody issuance starts `ready` and is atomically claimed as `consumed` when the exact authenticated `open_custody` request is accepted, within 30 seconds. Each transition targets the current leaf, uses the next positive sequence and exact predecessor digest, is strictly later than its predecessor and before expiry, and has at most one successor. Expiry is derived. No consumed or abandoned state can be resurrected. Source grants bind the exact `open_staged` request, staged occurrence, collector handoff, and launcher-created single-document bundle seal. The adapter resolves and recomputes that seal, requires the exact operation ID/nonce, runtime profile, identity bindings, submitter/importer/launcher bindings, artifact and handoff, and checks both handoff and seal validity at issuance and use. Preparation grants bind the `prepare` request, grounded source grant, pending object, and exact bytes. A sealed grant binds the adapter's issuance time as `custody_evaluated_at`, the then-current accepted-bundle sequence, one current clearance, exact custody leaf/copy/backend, purpose, and exact bytes. A successful `open_custody` response repeats the check at the adapter-produced response time and current accepted-bundle sequence; a caller cannot select a historical time or sequence to bypass a later known restriction, quarantine, or tombstone. Runtime clock correctness and skew enforcement remain a later implementation prerequisite. The adapter rejects arbitrary object keys, roots, endpoints, namespace listing, overwrite, deletion, policy changes, restriction, or tombstone execution through this interface. Those administrative actions remain separate later services.

The operation table above is exhaustive. For each operation, a request sets exactly its required payload fields and descriptor roles; every other response-only or other-operation field is null. A successful response uses only the registered success outcome, success payload fields, and exact descriptor roles. A failed response uses only `outcome_code` (`rejected`, `retryable_failure`, or the operation-specific `corrupt`) and `error_code`: it carries no artifact, handle/preparation/capability token, backend/copy/custody value, durability receipt, or file descriptor. This prevents a failure message from minting success material.

`publish_no_replace` finalization does not create a migration-005 custody event. It produces operational evidence that the exact object is durable enough for the importer to proceed. SQLite still records the manifest-defined custody declaration transactionally. Deduplication never widens access, merges logical artifact identities, or authorizes another custody class.

## Clearance semantics

A clearance decision is immutable, content-addressed, and scoped to exactly `(byte_layer, sha256, byte_length)`. Its closed decision is `restricted_store_only`, `repository_eligible`, or `do_not_retain`. It records source/capture context references; retention, redistribution, derivative-use, privacy/sensitivity, size, permanence, and access conclusions; a hash-bound support reference; scanner policy/results; conditions and limitations; the authenticated decision maker; a distinct independent checker; decision, not-before, expiry, and recording times; and four self-resolving commitments: the exact runtime-profile record digest, exact identity-binding record digest, exact clearance operational-profile bytes, and a canonical digest of the same decision record's artifact-and-decision scope. Changing a supporting record does not silently alter that semantic scope, but it does change the complete clearance-record digest.

A later revocation or supersession is a new predecessor-bound record, never an edit. Version 1 permits exactly one terminal transition for a decision: sequence 1, no prior transition, and either `revoked` with a null replacement or `superseded` with a distinct replacement decision for the same artifact. Expiry is derived from the pinned operation time and does not require a mutation. Immediately before promotion the launcher/importer requires one matching, current, unrevoked, unsuperseded, unexpired decision and rechecks its hash, scope, actors, and scanner ages.

Every decision fixes `contains_personal_data` and `contains_credentials` to false, requires a distinct human decider and checker, and carries the exact scanner-result set and causal decision/not-before/expiry/recording times. The decision matrix is total; no other cross-field combination is accepted:

| Decision | Retention | Redistribution | Derivatives | Sensitivity | Git permanence | Four repository declarations |
|---|---|---|---|---|---|---|
| `restricted_store_only` | `pilot_only` | `none` | `internal_only` | `restricted` | false | all false |
| `repository_eligible` | `repository_history` | `repository` | `repository_allowed` | `repository_safe` | true | all exactly true |
| `do_not_retain` | `none` | `none` | `none` | `restricted` | false | all false |

`restricted_store_only` is the only permitted decision for the initial one-document pilot. `do_not_retain` cannot create an artifact or live custody reference. Revocation reasons are `new_information`, `operator_withdrawal`, or `policy_changed`; supersession reasons are `new_information`, `policy_changed`, or `record_corrected`. None of these values proves copyright permission, absence of personal data, malware safety, officiality, or legal authority. The first real clearance and every human identity behind it require later separate approval; D9.0 contains synthetic records only.

The four repository declarations are exactly `redistribution_eligible`, `no_sensitive_data`, `size_eligible`, and `permanent_history_acknowledged`; null or omission is never equivalent to false or true.

The same closed schema has a structurally separate `prepromotion_authorization` variant. Immediately before promotion, the independent verifier semantically authorizes one exact operation ID/nonce after pinning the launcher bundle seal, the collector handoff, the physical candidate-file seal, the current clearance decision and semantic scope, the exact artifact, the current custody-leaf projection, the accepted knowledge sequence, runtime profile, and identity bindings. `evaluated_at` is the verifier's semantic evaluation time. The clearance broker persists those already authorized bytes through its fixed-function register and supplies the protected `persisted_at` knowledge boundary; persistence does not let it substitute for the verifier. The contract requires `evaluated_at <= persisted_at < expires_at`, resolves the broker binding at `persisted_at`, and requires persistence before both the promotion event and that journal event's protected append time. A record inserted later with a backdated evaluation cannot authorize an earlier promotion. The record cannot be reused across an operation, artifact, candidate, clearance, handoff, seal, runtime, or custody leaf. Revocation, supersession, expiry, or mismatch of any pinned prerequisite blocks promotion. The `promotion_started` journal event must name this exact record digest.

## Operation journal and recovery states

The journal format is append-intended until a later independent append broker and filesystem policy enforce append-only behavior. Each immutable event contains a journal ID, positive sequence, previous-event digest or a fixed genesis value, operation ID and nonce, semantic `event_at`, broker-protected `persisted_at`, originating component binding and executable digest, the distinct `journal_broker` binding that recorded it, runtime-profile and identity-binding digests, nullable validated bundle references, target and observed logical-state seals, phase, disposition, minimized object/count facts, nullable candidate/backup digests, and either a closed error reference or null. `event_at` states when the responsible component says the event occurred; `persisted_at` states when the authenticated fixed-function broker appended it and is the knowledge boundary. The contract requires `event_at <= persisted_at`, validates the semantic producer at `event_at`, validates the broker at `persisted_at`, projects permits at `persisted_at`, and requires both times to increase strictly through the chain. A record appended after revocation, terminalization, or expiry cannot regain authority by backdating `event_at`. Every event in a chain preserves the same operation ID/nonce, runtime profile, identity bindings, bundle tuple when present, and target state; only the registered event-specific fields may evolve. `target_logical_state` is the exact state expected at operation entry: the genesis-empty state for first bootstrap, the prior canonical state for document import, the proven empty disposable target for reconstruction, or the already independently verified canonical state for post-promotion completion. `observed_logical_state`, when the event rule requires or permits it, is the exact state independently observed at that semantic event boundary and must have been available by `event_at`; later broker persistence does not let a future seal satisfy a backdated event. Neither field is a caller assertion, and an observation never silently changes the target. `component_binding_code` is the semantic producer of the event; `recorded_by_binding_code` and `persisted_at` belong to the append broker and cannot be used to erase or impersonate that origin. Likewise, the fixed database writer transports and applies an already validated typed canonical plan but is not the semantic producer of manifest source claims, clearance decisions, permits, state seals, or operational authorization. The exact origin matrix is machine-readable: `operation_started` comes from the launcher; durable-custody, candidate-commit, candidate-seal, promotion-start, promotion-observed, and completion events come respectively from custody adapter, writer, verifier, promoter, verifier, and importer; generic stage events and `recovery_required` come only from the one service role assigned to their exact stage. The record excludes raw content, headers, full URLs/query strings, unrestricted paths, scanner text, credentials, and stack traces.

The closed error stages are:

`startup`, `authorization`, `operation_lock`, `input_open`, `manifest_parse`, `manifest_contract`, `runtime_binding`, `handoff_validation`, `preflight`, `staging_snapshot`, `screening`, `clearance`, `custody_prepare`, `custody_backup`, `candidate_build`, `database_transaction`, `projection`, `independent_verification`, `prior_backup`, `promotion`, `post_promotion_verification`, `final_backup`, `reconciliation`, `recovery`, and `completion`.

Every stable error code has exactly one registry entry binding it to one stage, one retryable boolean, and one recovery class. Consumers reject an unregistered code or a conflicting combination. Recovery classes are:

- `none`: no recovery action is required; the separate retryability classification still decides whether a new operation is allowed;
- `reconcile_orphan`: canonical SQLite is unchanged, but a durable unreferenced object requires reconciliation;
- `discard_candidate`: a verified noncanonical candidate may be discarded after its state is classified;
- `complete_post_promotion`: the canonical receipt may exist and only read-only classification plus privileged completion is allowed;
- `restore_verified_generation`: a separately verified prior generation is the only permitted restoration candidate;
- `capacity_incident`: resource/disk/database capacity must be restored and independently checked before retry;
- `security_incident`: preserve bounded evidence, lock the write path, and escalate; no automatic retry;
- `forensic_hold`: preserve state, lock ordinary writes, and require a separately authorized investigation.

Retryability is a separate closed value: `never`, `new_operation_same_bundle`, `recovery_only`, or `human_decision_required`. No recovery class silently grants permission to retry.

For a journal event with no error, `error_code` is null, `retryability_code` is `never`, and `recovery_class_code` is `none`. When an error is present, its stage, retryability, recovery class, canonical effect, disposition, observed-state policy, and bundle-reference policy must equal the one registered tuple. The error registry is total: each of its 60 codes has exactly one result/effect row and exactly one bundle-reference row. An error raised before trusted bundle identity is established requires all three bundle fields to be null; an error after identity validation requires all three; `INTERNAL_CONTRACT_VIOLATION` alone permits either complete absence or a complete tuple because it can detect an internal fault on either side of that boundary. Partial tuples are always rejected. `result_outcome_code` is null except for the registered `recovery_required` and `operation_completed` terminal rows. The schema closes the individual fields; the classifications registry closes these cross-field combinations.

The stable code registry is closed and versioned. In particular, parse/schema/digest/identity conflicts are not retryable unchanged; scanner unavailability or timeout may permit `new_operation_same_bundle`; malware, secret, personal-data, root-escape, identity-spoof, seal, or corruption failures are security or human-decision events; capacity failures are never silently retried; and a possibly completed promotion requires `complete_post_promotion` or a stronger hold with retryability `recovery_only`.

The canonical-operation effect is independent of process success. The closed `canonical_effect_code` values are:

- `none_verified`: read-only checks prove this invocation did not promote a canonical generation;
- `promoted_verified`: this invocation promoted and then independently verified the new canonical generation;
- `possibly_promoted`: promotion may have occurred but the canonical receipt/head has not yet been safely classified;
- `unknown`: available evidence cannot establish either of the preceding conditions.

This replaces the ambiguous Decision 9 draft field `candidate_promoted`. A `recovery_required` result uses `possibly_promoted` or `unknown` while promotion remains unclassified. It may use `promoted_verified` only for the closed post-promotion final-backup or journal-completion failures after the exact canonical state is independently verified; this reports an already completed promotion and grants no new canonical write. In pilot contract version 1, a `recovered` invocation is restricted to an independently verified path with `none_verified`; it cannot report or perform a new canonical promotion.

The journal matrix is total. “Optional” still means the value must satisfy its registered phase semantics when present; it never permits an arbitrary combination.

Promotion continuity is exact. The candidate-file hash is identical from `candidate_committed` through candidate seal, promotion start, and promotion observation. The prior-backup hash is identical at promotion start and observation. The state committed by `candidate_sealed` is the state later observed at promotion or at the applicable terminal boundary. Because the journal schema carries the candidate-file hash rather than a seal-record digest, the candidate-file-seal record must resolve uniquely by the exact tuple `(operation_id, operation_nonce, candidate_file_sha256)`, match the candidate state, and have `produced_at` no later than the `candidate_sealed` event. An unrelated seal of identical bytes in another operation neither satisfies nor invalidates that tuple. Promotion start additionally pins the exact current pre-promotion authorization. A hash-shaped placeholder cannot satisfy any of these references.

Database row counts report effects of this invocation and are zero after its database transaction rolls back. Object counts report actual durable custody effects; a database rollback can therefore return zero rows and a positive `orphaned` object count because object finalization precedes SQLite. The result must never erase that fact.

Bundle ID/sequence/digest fields follow the total per-error rule above rather than a stage-name shortcut. They remain null for a rejected operation until the entire tuple has passed lexical shape, byte bounds, digest, and safe-to-echo validation; once trusted bundle identity is available, later failures must return that complete tuple. Error messages are fixed templates with bounded redacted parameters; they never echo untrusted full input. Output contains no evidence/candidate text, response headers, credential material, absolute paths, full URLs/query strings, scanner output, stack trace, OS username, UID, or unrestricted internal identifier.

## Logical-state seal

The logical seal is independent of local import time, filename, inode, filesystem path, database page layout, WAL state, or SQLite file digest. It deterministically commits to:

- canonical-lineage ID and profile/contract versions;
- ordered migration filenames and SHA-256 values for migrations 001–005;
- normalized complete schema inventory and its digest;
- receipt head: null genesis or exact sequence, bundle ID, bundle digest, and deterministic receipt-row digest; the physical receipt is resolved by that unique bundle tuple rather than an identifier absent from migration 005;
- exact principal roster ordered by positive ID, including kind, creator code, and deterministic creation time;
- all nine Tranche 2A table projections under the D9.0 raw deterministic-ID projection and declared-column ordering;
- every retained accepted manifest reopened from its approved byte resolver and canonical-digest recomputed, including every manifest that owns a conditional-request basis event;
- all 13 frozen legacy row-level digests plus complete pre-005 schema definitions;
- Tranche 1A language/jurisdiction tables and every other prohibited surface, even when empty;
- the prior logical-state-seal digest where a transition is expected.

The seal payload and ordering are fixed by schema and golden vector. A physical `candidate_file_seal` is a separate operational record that binds exactly the operation ID/nonce; expected prior and candidate logical-state references; closed-file SHA-256 and byte length; device and inode numbers; link count exactly 1; mode exactly `0400`; verifier binding; production time; and expiry. It contains no owner field, path, or parent-directory-handle field; those platform facts remain independently checked implementation inputs rather than invented contract members. The physical seal protects one promotion operation and must never be used as a reconstruction identity.

## Secret exclusion, redaction, and hostile inputs

Closed schemas reject every undeclared field. The contract validator separately rejects credential-shaped field names at any nesting depth, including token-boundary variants of `authorization`, `cookie`, `credential`, `password`, `passwd`, `secret`, `token`, `api_key`, `apikey`, `private_key`, `signing_key`, `access_key`, `client_secret`, `refresh_token`, `bearer_token`, `session_cookie`, and `auth_token`. Schema patterns and the validator reject embedded NUL, C0 controls, and DEL in identifiers, paths, messages, and log-safe values.

The validator also applies value scanning to synthetic contract instances for private-key markers, authorization/cookie syntax, common bearer/token assignment forms, credential-bearing URLs, signed-query indicators, absolute paths where only logical handles are allowed, and a fixed synthetic personal-data marker. These checks prove rejection of the tested shapes only. JSON Schema and the offline validator cannot prove that arbitrary input contains no secret, personal data, or malware, or that operating-system resource controls are active. Later implementations must use approved scanners, minimization, fixed error templates, sanitized environments, core-dump suppression, access-controlled handling, and enforcement of every frozen resource ceiling.

Artifact/document bytes are never embedded in the JSON contract records. The design fixture set includes one independently hashed 32-byte synthetic object solely to exercise exact-byte resolution; it is not evidence or a real document. All fixtures use invented identities, paths, hashes, commits, objects, and content. Invalid credential fixtures should be generated or clearly isolated as non-secrets so repository scanning cannot mistake them for usable credentials.

## Failure and recovery contract

The journal/result contracts distinguish these boundaries:

1. Before CAS preparation, a failure has `none_verified` and no durable evidence effect.
2. A temporary adapter object may be abandoned or reconciled only under the exact operation ID/nonce and protected preparation issuance/transition history.
3. A published but unreferenced object is an orphan candidate; it does not justify a custody row and cannot be deleted before reference/hold/grace checks.
4. A candidate-database failure rolls back all SQL but may leave the prior orphan candidate.
5. A committed candidate not promoted is disposable after verification; canonical remains unchanged.
6. A failure before atomic rename remains `none_verified` only after the old canonical generation and receipt head are verified.
7. An interruption at rename is `possibly_promoted` or `unknown` until held descriptors, seals, journal, canonical receipt/head, and verified prior backup resolve it.
8. After a verified canonical receipt exists, recovery may repair only noncanonical journal/backup completion. It must not reapply SQL, invent custody events, or automatically restore the older database.
9. Ambiguity locks the write profile and requires `human_decision_required`.

Retrying an operation creates a new journal attempt. It creates no new retrieval or processing evidence unless a separately reviewed manifest explicitly declares a new occurrence.

## Field provenance and data handling

The schemas are authoritative for structure and value shape. The machine-readable [`field-registry-v1.json`](schema/d9-0/field-registry-v1.json) applies a complete classification to every reachable schema leaf. For a non-union schema it uses one default plus explicit JSON-Pointer-pattern overrides. For a union it first selects exactly one closed discriminator variant—collector receipt, bootstrap bundle seal, or single-document bundle seal; bootstrap issuance, transition, replay certificate, reconstruction permit, or post-promotion-completion permit; custody request versus response; capability source/preparation/sealed issuance or transition; clearance decision, revocation, supersession, or pre-promotion authorization—and then applies that variant's producer/consumer/storage/confidentiality/state/digest classification. Field-registry pointer patterns are RFC 6901-style **subtree-prefix** matches with one-segment `*` wildcards; digest-binding pointer patterns are exact-length matches. The validator fails if a leaf is uncovered, a selector overlaps or misses a variant, or an override is unused or ambiguous. It also pins the complete effective mapping so changing a producer, consumer, storage class, confidentiality, state class, digest treatment, resolver, or payload profile to another syntactically valid value still fails. A capability envelope's message sender is its carrier; the field overrides name the protected capability issuer as the semantic producer. The registry is the exact field-level map of trusted producer, consumer, instance storage, confidentiality, canonical/operational state class, and digest coverage. The following summary is explanatory:

|---|---|---|---|---|---|

## Later implementation ownership

D9.0 proposes to freeze descriptions and validation fixtures only. The runtime profile, binding map, seals, and registries are contracts for later components; their presence in this repository does not establish that a process sandbox, authenticated peer, append-only store, scanner, backup, custody durability, or write isolation exists:

- **D9.1** must implement launcher identity binding, active binding/handoff generation and revocation selection, IPC peer checks, immutable runtime-profile loading, handoff/seal verification, authenticated trusted-launcher append brokering, protected short-lived capability/permit state, per-permit logical-handle issuance/revocation, and a synthetic bootstrap dry run. It must adversarially prove those runtime restrictions and must not execute the real ceremony.
- **D9.2** must implement the secure manifest opener, approved evidence canonicalizer, semantic preflight, typed plan, fixed writer, candidate clone, full projection verifier, logical seals, result generation, and write-surface isolation.
- **D9.3** must implement the restricted local CAS adapter, IPC framing/descriptor passing, no-replace durability, lock, operation journal, crash recovery, and conservative orphan reconciliation.
- **D9.4** must implement resource-bounded scanners, privacy/secret/malware procedures, exact clearance register, rights decision workflow, and separately privileged restriction/relocation/tombstone operations.
- **D9.5** must implement independently encrypted backup, inventory, restore, and separately approved deletion-aware recovery.
- **D9.6** must run the complete synthetic fault/mutation/security matrix against the real components and obtain independent review.
- **D9.7** alone may request separate authorization to execute the bootstrap ceremony and, afterward, separately authorize one real raw-document bundle.
- **D9.8** remains a separately selected and approved hosted production profile.

## Approval boundary

Approval of D9.0 would freeze these version-1 schemas, limits, classifications, canonicalization rules, and synthetic fixtures as inputs to later implementation reviews. It would not approve any executable component, operational profile instance, principal creation, credential, rights decision, source retrieval, artifact storage, bootstrap transition, database write, evidence import, legal assertion, public exposure, or production use.

Until the relevant later D9 tranches are implemented, independently reviewed, and separately approved, all `atlas_*` tables remain empty and the frontend remains exclusively backed by legacy v1 data.
